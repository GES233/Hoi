# Hoi

一个纯本地、以运动习惯为主线的生活记录应用。名字来源于

hoi 不以「是否镰刀位」为目标，而是帮助自己：

> 给今天一个做得到的最低版本，让真实发生的运动留下来。

结合轻量运动计划、训练记录与回顾，同时保留饮食记录，后续逐步加入睡眠和精神状态记录。

目标平台：Android、Windows。

---

## 项目状态

本项目处于个人使用的早期开发阶段。

以下“产品设计”包含尚未实现的功能，不代表当前代码已经支持。开发完成后，应同步更新本节与开发路线。

根据当前项目说明，已有能力包括：

- 按日期查看记录，可回到今天。
- 添加饮食记录与常用食物。
- 实际训练记录闭环：开始 / 暂停 / 继续 / 结束训练，动作与组（次数或时长）记录，补记、编辑与删除已完成训练。
- 组级计时小秒表：动作卡内「开始一组」一键计时，结束并保存为时长组；训练总用时为页面顶部紧凑信息。
- 同时至多一场进行中训练，切换页面与重启后可恢复。
- 最低／常规两档运动方案：创建、编辑、删除，关联时保存判定快照，按实际记录实时判定达标。
- 每日休息标记（可选备注），不表达为失败。
- 每周运动次数与时长目标，本周进度与落实点阵。
- 首页按行动入口组织：日期导航、今日方案、开始/补记入口、进行中训练、当日运动记录、饮食入口与摄入摘要、本周概览。
- 本地 SQLite 数据存储。

下一阶段重点：

- 睡眠与精神状态记录。
- 更详细的周回顾。

## 产品原则

### 1. 最低方案完成，就是一次成功

最低方案是时间少、状态一般时仍然容易执行的版本。

完成最低后，界面应明确反馈：

> 今天的最低方案已完成。

常规方案是有余力时的选择，不是完成最低后还欠下的任务。

不将“只完成最低”展示为失败或低完成率。

### 2. 计划与事实分开

计划表达“准备做什么”，记录表达“实际做了什么”。

- 没有计划，也可以运动和记录。
- 选择一个方案，不代表已经完成。
- 运动记录满足条件后，才能判定方案完成。
- 不通过点击“已完成”凭空生成运动次数、时长或组数。

### 3. 开始与补记同等重要

既支持运动前开始记录，也支持过程中、事后补记。

不要求用户必须先启动计时器，才能留下运动记录。

### 4. 记录尽量轻

- 不要求所有运动填写相同字段。
- 感受与备注始终可选。
- 不知道准确时间时，可以只记录日期。
- 不为了展示完整而迫使用户编造数据。

### 5. 保底不等于忽略恢复

允许标记休息或暂停，可选说明原因。

休息、身体不适、暂停计划，不应被默认表达为失败。

### 6. 不做不透明的综合评分

不把心肺、抗阻、功能训练硬换算为一个“健康分数”。

分别展示真实的次数、时长、组数与计划完成情况。

## 核心概念

### 运动类别

当前主要使用：

- 心肺。
- 抗阻。
- 核心。

后续考虑将核心、灵活性、爆发力等组织到“功能训练”中。

类别用于组织与回顾，不决定记录方式。

例如：

| 动作 | 类别 | 常用记录方式 |
| --- | --- | --- |
| 散步、骑行 | 心肺 | 时长，可选距离 |
| 飞鸟 | 抗阻 | 组、次数，可选重量 |
| Hollow body | 核心 | 组、持续秒数 |
| 灵活性练习 | 功能 | 时长或组次 |

第一版不需要复杂的分类或标签管理系统。

### 一次训练

一次训练是一次实际运动过程的容器，可以包含多个动作、多个类别。

例如：

- 飞鸟 3 组。
- Hollow body 2 组。
- 结束后记录一句感受。

以上属于同一次训练，而不是 5 次运动。

### 动作与组

一个动作可以记录：

- 持续时长。
- 若干组次数记录。
- 若干组持续时间记录。
- 可选重量。
- 可选备注。

字段按动作需要使用，不强制全部填写。

### 运动方案

运动方案表达“这个动作准备做到什么程度”。

第一版一个方案绑定一个动作，并使用一种判定指标：

- 持续时长。
- 有效组数。

方案包含：

- 名称。
- 关联动作及类别。
- 最低阈值。
- 常规阈值。
- 可选说明。

最低与常规使用相同指标，常规阈值不得低于最低阈值。

示例仅用于说明交互，不是训练建议：

- 散步：最低 5 分钟，常规 20 分钟。
- 自选抗阻动作：最低 1 组，常规 3 组。
- 自选核心动作：最低 1 组，常规 2 组。

一次实际训练仍可添加其他动作，但其他动作不自动替代方案绑定的动作。

复合方案、完整训练模板、复杂替代规则暂不纳入第一版。

### 其他

主要用作辅助判断，包括睡眠状态的主观评价以及应激水平的主管评价。

## 最低与常规的判定

### 每日保底

第一版默认：

> 当天任意一次已完成训练满足一个关联方案的最低条件，即完成当日保底。

不要求心肺、抗阻、核心每天分别完成最低量。

### 判定范围

第一版在单次训练内累计关联动作的有效记录。

暂不做多次训练之间的累计达标。

- 时长型：累计该动作实际记录的持续时长。
- 组数型：累计该动作有效保存的组记录。
- 次数或持续时间必须大于零，才算有效组。
- 未保存的草稿、尚未结束的训练不参与完成判定。

### 档位关系

- 未达到最低：已有记录，但尚未达到最低。
- 达到最低：最低方案完成。
- 达到常规：最低与常规均完成。
- 超过常规：照常记录实际量，不要求继续追逐第三档。

不把最低与常规相加计算任务总量。

### 历史记录

关联方案时，应保存判定所需的方案快照。

修改或删除方案后，不得悄悄改变已有训练的历史达标结果。

编辑、删除实际运动记录后，应按该训练保存的判定条件重新计算。

### 未设置方案

未设置最低方案时，显示“尚未设置最低方案”。

不能把“没有方案”误判为“已达标”，也不自动生成训练要求。

## 两条记录路径

### 开始运动

流程：

1. 选择运动方案，或直接开始自由训练。
2. 创建一次进行中的训练。
3. 按需计时、记录动作或记录一组。
4. 结束训练。
5. 可选填写感受。
6. 保存并更新当日与本周统计。

开始运动不等于所有动作都必须使用秒表。

- 心肺训练以时长记录为主。
- 抗阻训练以组记录为主。
- 静态支撑可以记录每组持续秒数。

第一版优先实现训练总计时与组记录，不要求同时实现复杂的动作计时和休息倒计时。

### 补记运动

流程：

1. 选择日期。
2. 添加动作、时长或组记录。
3. 可选关联运动方案。
4. 可选填写训练总用时与感受。
5. 保存为一次已完成训练。

开始与补记最终使用同一种实际记录结构。

补记可以只知道日期，不要求提供精确开始时间。

## 计时与统计规则

### 训练总用时

训练总用时可以包含组间休息，但不包含显式暂停的时间。

训练总用时与动作持续时长是不同概念：

- 训练总用时：这次训练占用了多久。
- 动作持续时长：某个动作实际记录了多久。

不能把训练总用时自动分配给每个动作，也不能与动作时长重复相加。

单一时长型运动结束时，可用计时结果预填动作时长，但需要用户确认。

### 进行中训练

- 第一版同时只允许一场进行中的训练。
- 切换页面不应丢失训练状态。
- 应用重启后应能恢复进行中的训练。
- 计时依赖持久化的时间信息，而不是只依赖页面内的定时器。
- 暂停期间不累计训练用时。

### 日期

- 实时开始的训练归属开始时的本地日期。
- 跨午夜的训练第一版不自动拆分。
- 补记使用用户选择的日期。
- 日期统一使用项目现有的日期归一化规则。

### 周统计

- 运动次数按已完成训练统计，不按动作或组统计。
- 一次混合训练仍然只计一次。
- 周时长统计已记录的训练总用时。
- 未填写总用时的补记可以计入次数，但不凭空推算分钟数。
- 编辑、删除记录后同步更新统计。
- 不把一次混合训练的完整时长重复计入多个类别。

## 首页方向

首页优先回答：

1. 今天准备做什么？
2. 现在可以怎样开始？
3. 今天实际做了什么？

建议顺序：

1. 紧凑的日期导航与“回到今天”。
2. 今日最低／常规方案。
3. “开始运动”“补记运动”两个清晰入口。
4. 进行中的训练。
5. 今日运动记录。
6. 饮食记录入口与摘要。
7. 紧凑的本周概览。

最低完成后明确展示成功状态，常规仍可选。

不使用大面积热量卡作为首页最主要内容。

按钮不能遮挡记录列表；图标操作需要有明确含义或文字说明。

### 饮食与热量

保留已有饮食与常用食物能力。

如果运动消耗仅来自已记录运动，应使用“已记录运动消耗（估算）”等准确名称。

不将“饮食摄入减去已记录运动消耗”表达为可靠的全天净能量。

暂不新增自动热量估算或饮食分析。

## 回顾方向

回顾主要回答：

- 这周实际运动了多少次、多久？
- 哪些天完成了最低方案？
- 哪些天完成了常规方案？
- 主要做了哪些类别？
- 下周想继续什么、调整什么？

区分：

- 无记录。
- 有运动记录但未达最低。
- 最低完成。
- 常规完成。
- 主动休息或暂停。

原因由用户填写，不由应用猜测。

不以漏记一次为由否定此前的记录。

## 开发约定

- 数据库定义与查询放在 `AppDatabase`。
- 状态管理放在 `providers/`。
- UI 按 screen / widget 分层。
- 不手改 `database.g.dart`。
- 修改 drift 表后重新运行代码生成。
- 保留已有饮食、常用食物及日期查询能力。
- 不引入与本阶段无关的大型依赖。
- 数据加载、空状态与错误状态必须区分。

### 早期数据库调整

当前优先验证新记录模型，暂不要求兼容旧开发数据。

但：

- 不允许应用启动时自动删除数据库。
- 不允许 Agent 未经确认删除真实本地数据。
- 如果新结构需要重置开发数据库，应说明原因与操作方式，由开发者明确确认或手动执行。
- 数据库版本、初始化与代码生成必须保持自洽。

## 下一阶段验收场景

### 场景一：最低方案

创建一个最低 1 组、常规 3 组的自选动作方案。

完成并保存 1 组后结束训练：

- 显示最低完成。
- 不显示常规失败。
- 周运动次数增加 1，而不是按组增加。

### 场景二：继续记录

在同一次训练中继续保存其他组，并达到常规阈值：

- 同一次训练达到常规。
- 训练次数仍只计 1 次。
- 所有实际组记录保留。

### 场景三：混合训练

一次训练中记录抗阻动作与核心动作：

- 可以分别查看记录。
- 仍然是一次训练。
- 训练总用时不重复计算。

### 场景四：补记

补记昨天的一次运动并关联方案：

- 无需伪造精确开始时间。
- 满足条件时计入昨天的达标情况。
- 正确归入对应周。

### 场景五：恢复与修正

- 进行中训练重启后可恢复。
- 暂停时间不累计。
- 编辑或删除记录后，达标与统计重新计算。
- 修改方案阈值不改变此前训练保存的判定条件。
